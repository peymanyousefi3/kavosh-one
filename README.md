# Kavosh One

Private source repository for the multi-academy management platform for Kavosh Al and Robotics Academy Inc.

## Status

The owner authorized continuous backend implementation on 3 November 2026: implementation, tests, review and fixes proceed across milestones without another approval request. Visual UI/UX work still requires owner input. This remains an incomplete backend, not a production-ready academy or accounting platform. `backend-work.json` tracks the full approved scope and remaining dependencies; a passing milestone is not the end of the work.

Implemented: PostgreSQL migrations, tenant row policies and composite references, immutable academy-master identity, multi-role permissions with deny precedence, expiring/scoped bot credentials, shared rate limits, hub/pending-person creation and listing, audit history, credential revocation, bounded JSON/pagination, and transactional audit/outbox/idempotency records.

Human identity uses pinned Better Auth: invitation-only email/password signup, email verification, signed-in phone verification, master new-device MFA, optional MFA for others, trusted devices, encrypted single-use recovery codes, password recovery and session management. Unverified accounts cannot use academy APIs. The encrypted auth-message queue has a separate least-privilege delivery worker with SMTP/Twilio adapters; live providers are **not configured or delivery-verified**. The separate business-event outbox does not have an automation worker yet.

Role-template create/read/update/duplicate, scoped role assignments, effective-access inspection, supervisor hierarchy and exact-payload approval APIs are implemented. Masters self-approve; other actors require a permitted upper human reviewer. Expired/revoked bot credentials, changed authority and target versions invalidate pending proposals. Withdraw/reject history, reasons, audit and atomic rollback are preserved. Scoped denials exclude only affected hubs. Templates are academy-wide policy configuration; person-assignment views redact outside-scope segments. Editable geography/hubs, versioned courses, persistent classes/sessions and reviewed cancellation/rescheduling are also implemented; details and limitations are below.

Role-management screens, guardian-linked child contact verification, manual identity-recovery review, approvals for later domain modules, accounting, R2 uploads, BoldSign and other planned modules remain in progress/planned. No mock verification or public activation bypass exists.

The separate `kavosh-academy` repository contains the existing public-facing website and learning lab. Work here must not overwrite or deploy that project.

## Product workspaces

Overview, Academy, People, Learning, Finance, Reports, Community and Administration. Files, approvals, audit history and notifications are shared capabilities. External management agents use a scoped, documented API, with configurable approvals and limits.

- React/TypeScript with a supported standard Next.js/Node deployment.
- PostgreSQL as the authoritative transactional store.
- Private R2 object storage and permission-aware file browsing.
- Separate background workers for reports, notifications, payroll and automation.
- BoldSign integration, subject to verifying the existing account's API entitlement.
- VPS/container compatibility and custom domains.

## Repository rules

Keep this repository private. Never commit credentials, tokens, production databases, student/guardian records, private media, signatures or financial exports. Use synthetic data for tests. `.gitignore` is a convenience, not a secret scanner or an access-control boundary.

Implement in reviewable stages. Every completion claim needs evidence from the relevant persistence, authorization, accounting, browser or integration check. Paid integrations and production launch are separate authorization gates.

## Backend development

Use Node 22.13+ and pnpm 11.25.0. Install with `pnpm install --frozen-lockfile`. Run `pnpm typecheck`, `pnpm test`, `pnpm build` and then `pnpm test:http`. Tests use synthetic fixtures in an embedded PostgreSQL engine; setting `TEST_DATABASE_URL` to an isolated loopback PostgreSQL service runs the same suite over the real TCP driver in disposable, uniquely named databases. That integration account must be able to create databases. Never point tests at production.

The GitHub workflow checks both engines, migration repeatability, compilation, actual HTTP security responses, container execution and production dependency advisories. Real PostgreSQL also runs a bounded HTTP load test with 5,000 synthetic identities and 100 simultaneous connections (100 password logins, 300 session reads and 300 scoped business reads). It reports measured latency/errors, not a production capacity guarantee. Check the workflow result for the commit before treating CI as passed.

`pnpm db:migrate` uses only `MIGRATION_DATABASE_URL`. A database operator must separately provision a non-owner login belonging to `kavosh_runtime`, then place that login's connection string in runtime `DATABASE_URL`. No runtime account may inherit migration-owner, superuser or RLS-bypass privileges. Verified TLS is the default; plaintext is allowed only outside production for local development. Production must not receive migration credentials at all.

`pnpm bootstrap` reads `BOOTSTRAP_ACADEMY_NAME`, `BOOTSTRAP_MASTER_NAME`, `BOOTSTRAP_MASTER_EMAIL` and the migration connection from the operator's environment. It creates a provisioning-state academy with a pending human master and a seven-day bot credential. It prints the credential once for secure local storage; do not run in shared logs or paste it into chat. It does not send messages, verify users or activate an academy. This command provisions a new academy each time; do not rerun expecting to update an existing one.

Production packaging is provided in `Dockerfile`; the image runs as a non-root user and contains no database credentials. Real TLS, WAF/DDoS settings, failover, backups/restore and external delivery still require deployment verification. No deployment was performed. The intended deployment is an isolated `one.kavosh.ai` application on the existing VPS only after capacity/configuration review; the landing page must remain untouched.

## Human identity setup and flow

1. Apply migrations using the operator environment. Provision three **different** non-owner database logins: `kavosh_runtime` member for business APIs, `kavosh_identity` member for authentication, and `kavosh_delivery` member for the delivery worker. Never grant them `kavosh_identity_policy` or ownership/elevated roles. Identity is stored in its own private schema, not a separate physical database.
2. Configure web-only `APP_ORIGIN`, `AUTH_SECRET` (random, at least 32 characters), `IDENTITY_DATABASE_URL`, `DATABASE_URL` and, in production, `EDGE_AUTH_SECRET`. Keep migration credentials out of both web and worker environments. Production database TLS must verify certificates. Production origin must be HTTPS and exactly an origin, without trailing slash or path.
3. Provision the academy, then run `pnpm auth:invite` in the operator environment with `INVITE_ACADEMY_ID`, `INVITE_PERSON_ID`, `AUTH_SECRET` and `MIGRATION_DATABASE_URL`. The pending person's saved email is the invitation destination. Issuance expires old invitations and prints a private, single-use 48-hour invitation; do not put that output in shared logs. Invitation issuance is operator-only in this milestone.
4. The future interface supplies that invitation via `X-Kavosh-Invitation` to `POST /api/auth/sign-up/email`. The person verifies their email link, signs in, verifies a phone they control, then signs in again. Phone verification revokes existing sessions rather than upgrading an old session. A master completes SMS MFA, then accepts the invitation using `POST /api/auth/accept-invitation`. Only successful verified master acceptance activates a provisioning academy. Accepting an ordinary invitation grants no role automatically.
5. Use `/api/auth/memberships` to select an academy, then send `X-Academy-Id` with the host-only session cookie to business APIs. Membership, verification, MFA, academy state and roles are checked server-side. Cookies never authorize access to a foreign academy. Cookie-authenticated mutations require the exact configured Origin.

Every new master device requires an extra step; explicit trust lasts at most 30 days and rotates on use. Others can enable SMS or authenticator MFA. Recovery-code generation requires a fresh verified session and password; store the returned codes securely offline. Password reset/change revokes sessions and remembered-device grants without disabling MFA. There are no security questions or phone-only login/reset endpoints. Changing a verified phone and lost-all-factor recovery require a separately designed, audited support process; no unsafe bypass is provided.

The login interface should guide the user one task at a time (create account → verify email → verify phone → enter academy), automatically choosing the necessary next step, with plain-language errors and resend cooldowns. It must never read/store session tokens, put invitation/reset secrets in analytics, or reveal account existence in recovery messages. Reset links currently target the reserved `/account/recover#token=…` route; that interface is not built, so do not send onboarding messages to real users yet.

`pnpm auth:deliver` runs separately with `DELIVERY_DATABASE_URL`, the same `AUTH_SECRET`, SMTP settings and Twilio credentials from `.env.example`. It leases encrypted messages, retries failures up to three times with backoff, stops expired messages and scrubs payloads after delivery/expiry/final failure. SMTP requires TLS and valid certificates; Twilio calls use a fixed HTTPS endpoint. Provider acceptance is not proof of inbox/handset delivery. A crash after provider acceptance can cause a duplicate retry (at-least-once delivery). Real sender/domain/number setup, delivery receipts, regional regulatory registration and provider billing remain deployment gates.

At the reverse proxy, overwrite `X-Kavosh-Client-IP` from the trusted connection, remove client-supplied proxy headers and inject `X-Kavosh-Edge-Key`. Reject direct access to the application port. The application fails closed on missing/wrong production edge credentials. Add edge request timeouts, body limits, connection/rate limits and upstream DDoS protection; the app limiter alone is not DDoS protection. Never log query strings on verification endpoints, credentials, request bodies or cookies.

Retain `AUTH_SECRET` securely for encrypted recovery codes/messages and invitation digests; unplanned rotation makes them unusable. The running delivery worker hourly purges expired sessions/challenges, budgets older than two days, and expired invitations/scrubbed delivery rows after seven days. This does not delete academy records or audit/security history. Recovery-code regeneration signs out existing sessions; the interface must explain saving codes before signing in again. Before any production launch recheck Better Auth's announced 3 November security release and apply its stable fixes when published; 1.7.15 was the latest stable during this implementation check, not a guarantee against unpublished issues.

## API contract

`public/openapi.json` describes the implemented endpoints. `pnpm api:generate` updates the contract from the actual authentication and business schemas. Business endpoints accept either an expiring bot bearer token (academy derived from token) or a verified human cookie plus an authorized academy selection. Mutations require a UUID `Idempotency-Key`. People creation makes a pending record, not a login or enrollment.

The academy catalogue supports editable countries, provinces/regions, cities, hub contact/address/map coordinates, explicit time zones/currencies, multilingual labels and versioned courses with ordered modules. Hub-scoped readers see only permitted geography; shared and hub-specific courses have separate editing checks. Updates require the current version and preserve omitted fields. Sending a modules array replaces that ordered outline and retains the prior immutable snapshot. Archive rather than delete historical records. Active children prevent geographic archival. Minimal legacy hubs are flagged `setup_complete=false` until their location/time-zone/currency settings are explicitly supplied; no values are guessed. Course bodies are limited to 1 MiB and 100 modules; ordinary business bodies remain limited to 16 KiB. Classes, calendars, enrollment and the other items marked incomplete in `backend-work.json` are not implemented by this catalogue batch.

`POST /api/v1/calendar/preview` compiles weekly patterns, interval weeks, explicit irregular dates, overnight sessions and named excluded dates in the selected hub's explicitly configured time zone. It needs hub viewing rights, has a 128 KiB body limit, does not require an idempotency key, and is allowed during read-only service because it saves no domain records. Each weekly request covers at most 366 inclusive dates, with at most 500 total sessions. Ambiguous/nonexistent local times are rejected unless the caller explicitly selects earlier/later resolution; results retain requested and resolved local times, UTC instants, offsets, time-zone database version and actual duration. Overlapping sessions within the same compiled class schedule are rejected, while touching intervals are allowed. An unmatched exclusion remains visible rather than disappearing. The maintained Temporal polyfill supplies date/time-zone calculations rather than a custom DST algorithm.

`/api/v1/classes` persists classes, generated or configured codes, a pinned curriculum revision and an atomic first schedule. Append further schedule batches with the current class version; existing sessions are never silently replaced. A class retains its original time zone when hub settings change. Class mode/link changes set defaults for later sessions only. Session/schedule views are permission-filtered, paginated, and preserve holiday evidence. The PostgreSQL migration account must be permitted to install the standard `btree_gist` extension: its exclusion constraint prevents same-class session overlaps even during concurrent writes. Touching intervals and different classes at the same time remain valid.

`POST /api/v1/sessions/{id}/change` requests cancellation, restoration, rescheduling or online/in-person delivery changes with a reason. `sessions.request` grants request authority; `classes.edit` plus upper-human approval authority is required to review. Only the human master self-approves. Pending requests do not alter the calendar. Changed session data, revoked rights and time conflicts invalidate approval. Changes retain session identity and audit/outbox evidence; neither restoring a cancelled slot nor appending a schedule may create an overlap. Active classes prevent hub archival; scheduled future sessions prevent class archival. Dated administrative staff/student assignments are implemented below. Signed admission, payroll/report eligibility, calendar pathways and actual parent notification delivery remain incomplete.

Role assignments accept academy-wide `allHubs=true` or selected `hubIds`, `classIds` and `personIds`. The capability catalogue reports supported `scope_kinds`; a class selector cannot accidentally activate unrelated academy-wide feature rights. A selected class grants neither the whole hub nor access to unrelated people. A selected person filters basic people list/detail responses; it does not automatically reveal that person's other classes or restricted care/payroll data. Explicit class/person denials subtract from broad feature rights and cannot be undone by another allow role. Replacement assignments are checked as a complete allow/deny bundle against the delegator's authority. Reviewers must cover the exact typed case scope, not merely its parent hub name. Bot hub ceilings still constrain all record grants. Selectors use tenant-composite foreign keys and are reloaded with each request, with hidden assignment segments redacted from limited viewers. Each assignment supports up to 1,000 IDs of each kind, with 2,000 total selected resources and 128 KiB per access-replacement request.

Country, province/region and city permissions use `countryIds`, `regionIds` and `cityIds`. They include future hubs within the selected hierarchy, including initially empty areas. Finite hub authority cannot be delegated as dynamic geographic authority. Geographic and fixed-record denials survive delegation; incomplete legacy addresses fail closed when a regional denial might apply. Bot credential ceilings remain finite. Topology locks protect permission expansion and writers refresh their rights after waiting for a hub move. Academy-wide policy features cannot be activated by selecting a city. Geographic selectors, concurrent hub-move reads/writes and staffing passed real-PostgreSQL CI [41736770874](https://github.com/peymanyousefi3/kavosh-one/actions/runs/41736770874), with 147 passing checks. This evidence applies to commit `03468a0`, not subsequent changes.

Class/person scopes can be assigned explicitly; automatic teacher/guardian/student presets still require effective-dated staff/enrollment relationships and verification/consent gating. Do not infer a class roster from generic people rights or grant an entire hub as a shortcut. Application and SQL scope-containment implementations are checked for matching results and denial safety. Master updates to 5,000-recipient role presets retain the complete affected-version snapshot without per-recipient authorization queries; permissions are not cached across requests.

`/api/v1/classes/{id}/staff` provides dated teacher, TA and volunteer assignments with separate `staff.view`/`staff.edit` rights. The optional `on` filter is an inclusive date in the class's pinned time zone; combine `active=true` when selecting eligible assignments rather than historical/deactivated records. New assignments also require basic viewing rights for the selected human; bots and disabled people cannot be assigned. Overlapping active ranges for one person in one class are blocked natively; the same person may teach multiple classes simultaneously, with compensation deduplication still pending the payroll module. Updates require a version and reason, preserve omitted values and retain immutable revisions. Deactivation is reversible, not deletion. These assignments do not automatically grant account access or set compensation. Consent-gated enrollment and configurable relationship-derived presets remain pending.

`/api/v1/students` adds a separate private profile for an existing human, with legal/preferred names, exact birth date, optional configurable-text shirt size and an explicit academy/hub/person recruiter reference. `students.view`/`students.edit` are distinct from basic `people` rights and support selected-person, hub and geographic scopes. Directory responses omit birth dates, private notes and recruiter details. Corrections preserve omitted values and immutable private revisions; generic audit exposes only changed field names/version metadata, not profile values or correction notes. Creating a profile never activates a pending account, enrolls a student, creates a public page or declares agreement completion. Dated class membership is implemented separately below. Restricted care information, consent-gated family access, signing and financial allocations remain unfinished. Student profiles and the staff-history probing guard passed real-PostgreSQL/container CI [41738609813](https://github.com/peymanyousefi3/kavosh-one/actions/runs/41738609813), with 155 passing checks at commit `b16fc1e`.

`/api/v1/guardians` records private legal names and optional WeChat IDs under separate `guardians.view`/`guardians.edit` rights. Contact details appear only on authorized detail responses, not directory or general audit responses. A narrow tenant-bound database function reports current identity email/phone verification without granting the business connection access to password/MFA/session tables. Editors cannot set verification flags or replace verified contact details through profile inputs; those changes belong to identity verification/recovery flows. Draft profiles can be prepared before signup and remain explicitly unverified. Creating a guardian profile does not establish legal guardianship, grant student access or satisfy a consent/signature requirement. Guardian records, the verified-phone database invariant and the international DOB boundary passed real-PostgreSQL/container CI [41740412854](https://github.com/peymanyousefi3/kavosh-one/actions/runs/41740412854), with 163 passing checks at commit `a13bdc1`.

Migration 015 also enforces the identity gateway's E.164-format invariant in PostgreSQL: a phone cannot be marked verified while missing or malformed. It validates existing rows and fails for operator review if invalid legacy data exists; it never guesses numbers or silently changes verification evidence.

`/api/v1/students/{id}/guardians` manages private administrative family associations. `families.view`/`families.edit` person selectors refer to the **student**; initial guardian selection also requires `guardians.view` for that guardian. Creation, date/role changes and reinstatement require an upper human's approval; the immutable academy master self-approves. A non-master beneficiary (student or guardian) cannot review their own case. Each period has an inclusive start/exclusive end, millisecond precision, immutable history and native overlap protection for the same pair. A null creation start uses database time when approval is applied. Pending proposals pin profile versions and all existing periods for that pair. A later protective suspension invalidates older queued period changes.

Authorized humans can immediately suspend a specific period with a reason and critical audit/outbox evidence; reinstatement requires approval. This is a period-specific action, not a global guardian/account ban. Other independent periods must be reviewed separately. Ordinary audit responses omit the relationship members and private reasons; full history requires family-data access. Private approval cases additionally enforce their stored domain-view capability for list/detail/decision access, including the original requester after revocation. Retired handlers retain authorized history but cannot apply changes. Wrong-scope family requests and beneficiary-conflicted decisions are rejected before taking the school-wide policy-write lock, verified by instrumented positive/negative controls. These associations can be prepared for an unverified draft guardian but report current identity verification separately. They do not prove legal guardianship, complete signing, or automatically grant portal access. Consent-gated enrollment and configurable derived access remain pending. Family-module real-PostgreSQL/container CI [41743838879](https://github.com/peymanyousefi3/kavosh-one/actions/runs/41743838879) passed 177 checks at `9dc6db6`.

### Dated administrative enrollment

`/api/v1/classes/{id}/enrollments` and `/api/v1/enrollments/{id}` manage versioned student membership periods with separate `enrollments.view`/`enrollments.edit` rights. Joining and leaving dates are inclusive in the class's pinned time zone. Enabled periods cannot overlap for the same student/class or start before the pinned birth-date evidence; adjacent periods and simultaneous different classes are supported. Corrections preserve omitted values, immutable private history and the original student-profile basis unless explicitly refreshed. Requests require a reason and upper-human approval; only the school master self-approves. Non-master student/guardian beneficiaries cannot decide their own cases. Pending proposals pin class/profile/related-period versions, so intervening corrections require fresh review. Disabling a period is reversible, not deletion.

`classes/{id}/roster?on=YYYY-MM-DD` requires `rosters.view` and returns only date-selected student IDs/display names; the default is today in the class time zone. `sessions/{id}/roster` uses preserved local-start/offset/UTC evidence, rejects contradictory evidence and caller date overrides, and returns no candidates for cancelled sessions. Neither future joins, ended periods nor disabled periods appear outside their effective dates. Administrative enrollment lists intentionally retain future and void records for planning; they are not attendance selectors.

`students/{id}/enrollments` requires `registrations.view`, a separate read-only selected-student permission. It returns enabled registration summaries without peers, private profile fields, lesson URLs or internal approval history. Explicit student grants can follow that student's classes across hubs, but record-hub denials and bot credential ceilings still apply. Hub-only delegation cannot become an unrestricted selected-student grant; restricted delegators must preserve their exclusions. No automatic family/account rights are created. **These are administrative membership and roster-candidate APIs, not signed admission clearance or attendance authorization.** BoldSign signing, consent-gated attendance and relationship-derived access are still unfinished. Fifteen focused embedded checks pass. The frozen local suite passed 175 checks with one PostgreSQL-only load test skipped. Native-PostgreSQL/container CI [41748371676](https://github.com/peymanyousefi3/kavosh-one/actions/runs/41748371676) passed 193 checks at `6f40757`, including enrollment concurrency; migration repeatability, production build/HTTP, dependency audit and read-only non-root container checks also passed. ### BoldSign boundary (partial, not connected)

`src/integrations/boldsign.ts` implements raw-byte HMAC-SHA256 verification following the provider's [webhook specification](https://developers.boldsign.com/webhooks/verify-webhook-events/). It supports configured key rotation, constant-time digest comparisons and a fixed five-minute past/future clock window. Ambiguous/duplicate header fields and malformed signatures fail closed. The read-only document-status adapter requires an explicit US/CA/EU/AU account region and API key, uses fixed [regional endpoints](https://developers.boldsign.com/api-overview/versioning/), refuses redirects, limits streamed response bytes to 1 MiB and supplies a ten-second abort signal. It validates the requested document ID and minimal signer-status evidence, strips unrelated private form data and sanitizes failures. Unknown status names are retained as evidence, never interpreted as clearance.

Ten focused local checks passed, including independent OpenSSL/Web Crypto signature evidence and simulated provider responses. The frozen full local suite passed 185 checks with one PostgreSQL-only load test skipped; type checking, production build and HTTP smoke checks passed. A previous local run took roughly 106 minutes and its five-per-minute authentication assertion failed; the unchanged-policy frozen rerun passed that same assertion in 242 ms. This is recorded as a timing-sensitive test observation, not proof of a provider or production defect. The web process does not yet call this adapter or mount a webhook endpoint. Durable event deduplication, tenant/document/environment binding, verified status reconciliation workflow, signed-agreement lifecycle, evidence archival and admission gating remain unfinished; a valid HMAC or `Completed` response alone never authorizes attendance. No live BoldSign account, sending entitlement, API access or delivery is verified. No documents were sent.

These signing boundaries passed native-PostgreSQL/container CI [41762032074](https://github.com/peymanyousefi3/kavosh-one/actions/runs/41762032074) at `d9bbe41`, with 203 passing PostgreSQL checks. Provider responses remain simulated; this run does not prove a live BoldSign connection.

`/api/v1/agreements` manages private **unified enrollment agreement/waiver/consent definitions**, not signed PDFs. `agreements.view` and `agreements.edit` are separate hub/geographic rights; school-wide definitions require unrestricted school-wide rights. Creation, correction and duplication require upper-human review; the single school master self-approves. Ordinary role grants cannot bypass private approval visibility. Generic activity history omits private decision/withdrawal narratives; a read-time guard also redacts legacy private narratives without rewriting append-only records. Full notes remain in authorized cases.

Definitions contain the legal entity, country/jurisdiction, plain-text language variants (`en`, `fr`, `zh-CN`) and an optional BoldSign region/template mapping. Legal text preserves its whitespace and valid Unicode. Supplying `languages` replaces the complete language array; this is not an individual-language patch. The JSON definition hash is **not** a provider PDF hash or proof that remote template content matches. The register stores no API keys and never declares the text legally reviewed.

Hub ownership cannot be silently changed. Copy a specific historical revision with `/agreements/{id}/duplicate`, explicitly selecting the destination hub (or school-wide scope); a copy starts unavailable. Source viewing and destination editing are rechecked under policy locks. Pending cross-hub copy cases require private-case scope covering both ends. View permissions apply to current definitions and `/history`; directory responses omit full text. Text limits are 32,000 characters per language, 64,000 across languages and a 256-KiB request ceiling. Malformed UTF-8 JSON, unpaired surrogate text, null characters, duplicate languages, unknown fields and invented signing/eligibility flags are rejected. Availability only selects a configuration definition; it never activates a student or proves consent, legal validity, provider verification or eligibility. Signed-document generation/archival, real provider configuration and admission gating remain unfinished. ### R2 service boundary (partial; upload-link API defaults off)

### Private file metadata catalogue

`/api/v1/files` reserves and searches metadata; it does not upload bytes. Every record is anchored to exactly one school, hub, class or person. `files.view`/`files.edit` support the existing scoped permission system. Protected `student_private`, `guardian_private` and `agreement_definition` records also require the matching domain view/edit rights. Generic file access alone does not expose protected metadata/history. School-wide anchors require unrestricted school-wide rights. Person-bound files follow that person's current hub rather than leaving access with the former hub. Financial/payroll/signed-admission/private-learning domains and their attachment-specific access workflows are not implemented; do not treat a general record as an approved sensitive attachment.

Search covers name, description and tags, with case-insensitive literal matching (including `%` and `_`) and permission filtering before pagination. A native trigram index is installed; the tested query's actual index-plan usage has not been established. Metadata claims, anchor and domain cannot be silently changed. `/files/{id}/change` edits the name, description, tags or archive flag using an expected version; `/history` retains private revisions. General audit exposes versions/archive status, not filenames, descriptions or notes. Records explicitly return `awaiting_upload`, with no URL, verified content hash/type or clean status. Client MIME/size/hash fields are unverified claims. Names reject paths and malformed Unicode. No file-content access is granted by creating metadata.
